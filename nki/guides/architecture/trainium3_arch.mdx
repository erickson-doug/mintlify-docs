In this guide we dive into the hardware architecture of fourth-generation NeuronDevices: Trainium3. This guide highlights major architectural updates compared to the previous generation (Trainium2). We assume readers are familiar with the [Trainium/Inferentia2 architecture guide](/nki/guides/architecture/trainium_inferentia2_arch) and [Trainium2 architecture guide](/nki/guides/architecture/trainium2_arch) for the basics of NeuronDevice architecture.

The diagram below shows a block diagram of a Trainium3 device, which consists of:

- 8 NeuronCores (v4).
- 4 HBM stacks with a total device memory capacity of 144 GiB and bandwidth of 4.7 TB/s.
- 128 DMA (Direct Memory Access) engines to move data within and across devices.
- 20 CC-Cores for collective communication.
- 4 NeuronLink-v4 for device-to-device collective communication.

The rest of this guide discusses NeuronCore-v4's major architectural updates compared to NeuronCore-v3 that are relevant for NKI programmers.

## NeuronCore-v4 compute engine updates

The figure below is a simplified NeuronCore-v4 diagram of the compute engines and their connectivity to the two on-chip SRAMs, SBUF and PSUM.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-2.png" alt="NeuronCore-v4 compute engines and SRAM connectivity" />
</Frame>

The NeuronCore-v4 SBUF capacity is 32 MiB (up from 28 MiB in NeuronCore-v3), while PSUM capacity remains the same at 2 MiB. The engine data-path widths and frequencies are updated to the following:

| Architecture | Compute engine | Data-path width (elements/cycle) | Frequency (GHz) |
|---|---|---|---|
| Trainium3 | Tensor | 8×128 (MXFP8 dense input) or 2×128 (non-MXFP8 dense input) or 5×128 (sparse input); 1×128 (output) | 2.4 |
| | Vector | 512 BF16/FP16/FP8 input/output; 256 input/output for other data types | 1.2 |
| | Scalar | 256 BF16/FP16/FP8 input/output; 128 input/output for other data types | 1.2 |
| | GpSimd | 128 input/output for all data types | 1.2 |

Sync Engine hasn't changed since [previous Trainium architectures](/nki/guides/architecture/trainium_inferentia2_arch). Next, we go over major architectural updates to each compute engine.

## Tensor Engine

The Tensor Engine is optimized for tensor computations such as GEMM, CONV, and Transpose. A NeuronCore-v4 Tensor Engine delivers 315 MXFP8/MXFP4 TFLOPS, where MXFP8/MXFP4 are OCP (Open Compute Project) compliant data-type formats. Besides quantized data types, it delivers 79 BF16/FP16/TF32 and 20 FP32 TFLOPS of tensor computations. The rest of this section describes new architectural features.

### Quad-MXFP8/MXFP4 matmul performance

The NeuronCore-v4 Tensor Engine (TensorE) supports two new input data types: MXFP8 and MXFP4, where MX stands for "microscaling", as defined in the OCP standard. Microscaling is a subset of absmax (absolute-maximum quantization), where quantization scale factors are calculated using absolute maxima of fine-granularity groups of values, as opposed to having tensor- or channel-wise scale factors. It can significantly improve the amount of information preserved in the quantized values. The supported scaling group size is 32 — 32 MXFP8/MXFP4 elements along the matmul contraction dimension share the same 8-bit MX scale value. The Tensor Engine performs matrix multiplications of MXFP8 or MXFP4 input matrices and dequantization with the MX scales in a single instruction, with the output either in FP32 or BF16. We refer to MXFP8 and MXFP4 matmul as MX matmul. An MX matmul with either MXFP8 or MXFP4 runs at 4× the throughput compared to a BF16/FP16 matmul.

<Note>
  Multiplying an MXFP8 matrix with an MXFP4 matrix is also allowed.
</Note>

Logically, TensorE quadruples the MX matmul performance by quadrupling the maximum contraction dimension of the matmul instruction from 128 (for BF16/FP16) to 512, effectively presenting a 512×128 systolic array to the programmer. Under the hood, since the systolic array is still organized as a grid of 128×128 processing elements, each processing element performs four pairs of MX multiplications plus accumulation of the four multiplication results per cycle. This is similar to the Double-FP8 performance mode in the Trainium2 TensorE (discussed in the [Trainium2 architecture guide](/nki/guides/architecture/trainium2_arch)), but the data-layout requirements for MX matmul are distinct and discussed below.

Mathematically, an MX matmul instruction can perform a multiplication of a 128×512 matrix and a 512×512 matrix (M×K×N matmul, M=128, K=512, N=512). The figure below visualizes the two input matrices (x and y) and the matmul output matrix. Four elements (red, blue, yellow, and green) in the first row of x and in the first column of y are highlighted. These four elements are 128 (K/4) elements apart within the row and column. Each pair of same-colored elements gets multiplied, and the results are accumulated in the matmul operation.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-3.png" alt="MX matmul element layout" />
</Frame>

The figure below shows how the matrices should be laid out in SBUF in preparation for MX matmul. The x matrix is rotated 90° so that K is aligned with the SBUF partition dimension. We pack the four highlighted elements back-to-back along the free dimension. As a result, K=512 splits into (1) partition dimension of size 128 and (2) the most minor free dimension of size 4. The y (moving) matrix follows a similar four-element packing pattern. In NKI, programmers work with MX data using special quad (x4) packed data types: `float8_e5m2_x4`, `float8_e4m3fn_x4`, and `float4_e2m1fn_x4`.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-4.png" alt="MX matmul SBUF layout with x4 packed elements" />
</Frame>

Next we invoke `LoadStationary` and `MultiplyMoving` instructions. The `LoadStationary` instruction loads the MX stationary tensor (K/4=128, M=128, 4) into TensorE, which stores four MX data elements into a single processing element. The `MultiplyMoving` instruction streams the moving tensor horizontally across the loaded stationary tensor. Four elements of moving tensor are sent to the same processing element simultaneously so they can be multiplied with the corresponding loaded stationary elements.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-5.png" alt="LoadStationary and MultiplyMoving instructions for MX matmul" />
</Frame>

Since MX matmul in TensorE performs dequantization in addition to the multiplication, we discuss how the scale tensor is laid out in SBUF for TensorE consumption. The supported MX group size on NeuronCore-v4 TensorE is 32 elements along the contraction dimension. Each input MX matrix to the matmul operation therefore has its own scale tensor. The diagram below shows the full 32-element scaling group that includes the highlighted x4 elements within matrix x and y.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-6.png" alt="32-element MX scaling group layout" />
</Frame>

Focusing on the stationary data and scale tensor layout: the purple rectangle represents the 32-element scaling group, spanning 8 SBUF partitions (8P) and 4 elements per partition. A single scaling group corresponds to one 8-bit integer scale. So for every 32 partitions of the data tensor, we get 32/8=4 partitions of scale factors. The full scale tensor is split across four SBUF quadrants, where each quadrant holds 4 partitions of scales. The free dimension of the scale tensor is M=128 — 4× smaller than the data tensor, because the four packed colored elements belong to the same scaling group and share a single scale. Within each quadrant, 32−4=28 partitions are unused in the scale tensor below. Multiple scale tensors for different MX matmul instructions can be packed together to fill these unused partitions. See the MXFP NKI tutorial for more discussion on packed scales.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-7.png" alt="MX scale tensor layout across SBUF quadrants" />
</Frame>

The moving data and scale tensor layout follows the same rules. An MX matmul on TensorE requires four input tensors:

1. Stationary data
2. Stationary scale
3. Moving data
4. Moving scale

In NKI, programmers can define MX data tensors using the special x4 data types. The maximum tile size for stationary MX data tensor is `[128, 128]` in x4 data types (`[128, 512]` of actual values), while the maximum tile size for moving MX data tensor is `[128, 512]` in x4 data types (`[128, 2048]` of actual values). One convenience of the x4 datatypes is that the output matrix dimensions map directly to the sizes of the free dimensions of the input matrices. Similarly, the maximum tile size for stationary and moving MX scale tensors are `[128, 128]` and `[128, 512]` in `nl.uint8`, respectively. The API to invoke an MX matmul is [`nisa.nc_matmul_mx`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.nc_matmul_mx.html):

```python
nisa.nc_matmul_mx(dst, stationary, moving, stationary_scale, moving_scale)
```

### BF16 matmul results in PSUM

Prior to NeuronCore-v4, the Tensor Engine always passes FP32 matrix-multiplication results to PSUM unless transpose mode is enabled. Similarly, the PSUM buffer was restricted to FP32 near-memory accumulation (`fp32_psum_tensor += fp32_matmul_output`). Starting with NeuronCore-v4, the Tensor Engine allows the matrix-multiplication instruction ([`nisa.nc_matmul`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.nc_matmul.html)) to store BF16 data into the PSUM buffer directly, and to perform addition to a BF16 tensor stored in PSUM.

The accumulation performed during a matmul operation within the systolic array is still performed using FP32 data. When writing the matmul results into a BF16 PSUM tensor location, the downcast from FP32 to BF16 is performed immediately before the write. The downcast can use RNE (round nearest even) or SR (stochastic rounding) mode.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-8.png" alt="BF16 PSUM write flow" />
</Frame>

When adding the matmul results to an existing BF16 tensor stored in PSUM, the following operations are performed:

- The existing PSUM tensor is upcast to FP32.
- The PSUM tensor (now in FP32) and the TensorE output are added at FP32 precision.
- The result is converted to BF16 using the given rounding mode, and written back to PSUM.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-9.png" alt="BF16 PSUM add-accumulate flow" />
</Frame>

### Background transpose

The NeuronCore-v4 Tensor Engine supports a new background transpose functionality, which lets it run a transpose operation in parallel to another matrix multiplication (or another transpose). This achieves close to double performance on long chains of transposes, or overlaps a larger matrix multiplication with transpose operations in the background.

NKI programmers aren't required to enable background transpose explicitly to leverage the performance improvements. The decision to trigger background transpose is made automatically by the hardware.

## Vector Engine

The Vector Engine is optimized for vector computations where every element of the output depends on multiple input elements. Examples include axpi operations (Z = aX + Y), Layer Normalization, and Pooling. The NeuronCore-v4 Vector Engine delivers a total of 1.2 TFLOPS of FP32 computations and supports various input/output data types: FP8, FP16, BF16, TF32, FP32, INT8, INT16, and INT32.

### MX data-type quantization

The NeuronCore-v4 VectorE supports quantizing FP16/BF16 data to MXFP8 tensors (both data and scales) in a layout that TensorE can directly consume for MX matmul, as described in the quad-MXFP8/MXFP4 matmul performance section. An MxK MXFP8 matrix, where K is the contraction dimension, requires the following data and scale layout in SBUF:

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-10.png" alt="MXFP8 data and scale layout" />
</Frame>

The VectorE natively quantizes BF16/FP16 data to produce this layout using the `QuantizeMX` instruction. `QuantizeMX` calculates the required scales for each group of 32 values, divides them by the calculated scale, and casts to the target MXFP8 datatype (per the OCP specification):

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-11.png" alt="MX quantization flow" />
</Frame>

The source FP16/BF16 data must be in SBUF and must be in a layout that exactly matches the target MXFP8 data layout (QuantizeMX preserves the data layout). The target MXFP8 data and scales must also be in SBUF. The quantization instruction can quantize four input elements per partition per cycle (4× VectorE performance mode).

In NKI, programmers can perform MX data-type quantization using the [`nisa.quantize_mx`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.quantize_mx.html) API.

### Fast exponential evaluation

The NeuronCore-v4 Vector Engine introduces a new instruction to perform fast exponential evaluation ([`nisa.exponential`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.exponential.html)) at 4× the throughput compared to the [`nisa.activation`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.activation.html) (`op=nl.exp`) instruction on the Scalar Engine. The instruction on Vector Engine can also apply a subtraction before the exponential function and an accumulation after:

```python
# Inputs:
#   src tile [M, N]
#   max_value tile [M, 1]
# Outputs:
#   dst tile of the same shape [M, N]
#   reduce_res tile [M, 1]
for i in range(M):           # parallel (partition) dimension
    reduce_res[i, 0] = 0
    for j in range(N):       # sequential (free) dimension
        dst[i, j] = exp(src[i, j] - max_value[i, 0])
        reduce_res[i, 0] += dst[i, j]
```

This pattern speeds up Softmax, commonly on the critical path of long-context self-attention in LLMs:

$$
Softmax(X) = \frac{e^{X_i - max(X)}}{\sum_i e^{X_i - max(X)}}
$$

`X` is a vector of attention scores in the context of self-attention, which corresponds to a row in the `src` tile in the above instruction pseudo-code.

### XORWOW-based PRNG

The NeuronCore-v4 VectorE provides hardware support to produce PRNG (pseudo-random) values using XORWOW as the underlying algorithm. Compared to the LFSR-based algorithm used before NeuronCore-v4, XORWOW produces higher-quality random values. The NeuronCore-v4 VectorE can produce 4× 32-bit PRNG values per compute lane per engine cycle.

The NeuronCore-v4 VectorE introduces support for loading and storing XORWOW random states from and to SBUF (or PSUM), across all 128 compute lanes. Within each compute lane, four XORWOW random states are tracked to maintain the [`nisa.rand2`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.rand2.html) instruction throughput, with each state comprising 6 `uint32` values. For more details, see the [`nisa.rand_set_state`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.rand_set_state.html) and [`nisa.rand_get_state`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.rand_get_state.html) API documentation. This new state load/store capability allows users to save and restore random states for reproducible training runs more easily.

## Scalar Engine

The Scalar Engine is optimized for scalar computations in which every element of the output depends on one element of the input. The NeuronCore-v4 Scalar Engine delivers 1.2 TFLOPS of FP32 computations and supports various input/output data types: FP8, FP16, BF16, TF32, FP32, INT8, INT16, and INT32.

### Performance mode

The Trainium3 ScalarE now natively supports the [`tensor_scalar`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.tensor_scalar.html) and [`tensor_copy`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.tensor_copy.html) instructions (same as VectorE), and offers up to 2× performance uplift for BF16/FP16 datatypes, which is the same as the 2× performance mode on VectorE introduced with Trainium2. For those instructions, NKI users can select the execution engine, which can help offload either engine or load-balance between them, depending on workload characteristics.

### More flexible `nisa.activation`

<Note>
  The Activation2 instruction doesn't have an `nki.isa` API at this time.
</Note>

Trainium3 introduces the Activation2 instruction, which provides more flexibility compared to the existing Activation instruction. Unlike Activation — which only supports the combination of scale multiplication and bias addition — Activation2 supports bias subtraction and allows users to disable scale multiplication and bias addition entirely. Further, while Activation only supported `add` as a reduce command, Activation2 supports `add`, `max`, `min`, `absmax`, and `absmin` reductions.

## Data movement and DMA updates

### SBUF/PSUM indirect access

<Note>
  SBUF/PSUM indirect access for compute engines doesn't have an `nki.isa` API at this time.
</Note>

The NeuronCore-v4 SBUF/PSUM introduce a new indirect addressing mode for all compute engines (TensorE/VectorE/ScalarE/GpSimdE), which allows gathering or scattering SBUF and PSUM tensors along the free (F) dimension. Consider a tensor of shape `[128, 512]` in SBUF, which occupies 128 partitions with 512 elements per partition. Suppose you want to access only elements 0, 128, and 384 along the free dimension across all 128 partitions for a single computation operation (for example, `nisa.nc_matmul`):

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-12.png" alt="Non-uniform stride SBUF access" />
</Frame>

Since these three vectors don't have a uniform stride along the free dimension, the access pattern isn't a tensorized pattern (a regular N-dimensional access pattern). Prior to NeuronCore-v4, such an access pattern would require three separate instructions.

In NeuronCore-v4, all compute engines can perform a gather access pattern to directly access those three vectors in a single instruction:

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-13.png" alt="Indirect gather pattern" />
</Frame>

Similarly, an indirect scatter operation allows any engine to scatter a set of vectors into a target tensor:

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-14.png" alt="Indirect scatter pattern" />
</Frame>

Both styles of indirection use a separate offset tensor to encode which vectors to access.

### SBUF read-add-write

<Note>
  SBUF read-add-write doesn't have an `nki.isa` API at this time.
</Note>

NeuronCore-v4 introduces an enhanced SBUF capability that enables on-the-fly tensor accumulation near memory. This feature allows DMA engines to perform `B += A` operations, where tensor B resides in SBUF and tensor A can be sourced from any accessible memory location (HBM or SBUF). Tensors A and B can be BF16 or FP32 data types, but they must have a matching data type within a single DMA transfer performing the read-add-write. This near-memory accumulation maintains the same throughput as standard DMA copy operations to SBUF (compared to 50% DMA throughput via DMA collective compute engines prior to NeuronCore-v4), enabling efficient in-place tensor updates without additional memory overhead.

<Frame>
  <img src="/images/nki/img/arch_images/nki-trn3-arch-15.png" alt="SBUF read-add-write flow" />
</Frame>

### DMA traffic shaping

<Note>
  DMA traffic shaping doesn't have an `nki.isa` API at this time.
</Note>

Trainium3 DMA engines support traffic shaping, which enables configurable bandwidth allocation across different DMA operations. The feature supports 4 distinct classes of service, enabling fine-grained control over data-movement priorities. This is particularly beneficial when optimizing parallel computation and communication (collective operations) across multiple NeuronCores.
