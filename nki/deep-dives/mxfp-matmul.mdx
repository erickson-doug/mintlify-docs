## What is MXFP4/8 matrix multiplication?

MXFP4/8 matrix multiplication uses microscaling (MX) quantization as defined in the OCP standard. Unlike traditional quantization that uses tensor- or channel-wide scale factors, microscaling calculates quantization scales from small groups of values. Specifically, groups of 32 elements along the matrix-multiplication contraction dimension share the same 8-bit MX scale value.

This approach preserves significantly more information in quantized values by preventing high-magnitude outliers from "squeezing" the entire data distribution. The NeuronCore-v4 Tensor Engine performs matrix multiplication of MXFP4 or MXFP8 input matrices and dequantization with MX scales in a single instruction, achieving 4× throughput compared to BF16/FP16 matrix multiplication while outputting results in FP32 or BF16.

## Layout and tile-size requirements

Before diving into code examples of MX multiplication, it's important to review the layout and tile-size requirements of MX. MX quantized tensors are represented with separate data and scale tensors, each with distinct requirements.

### Data tensor

Compared to BF16/FP32 matrix multiplication, the performance uplift from Matmul-MX comes from the ability to contract 4× more elements during one matmul operation, since each TensorE processing element is able to perform four simultaneous FP4/FP8 multiply-accumulate computations. This means the maximum effective contraction dimension has increased from 128 → 512.

First, let's examine the tile-size constraints for MX so we can allocate the correct space for tensors. MX data is represented in NKI using quad (x4) packed data types ([`float8_e5m2_x4`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.language.float8_e5m2_x4.html), [`float8_e4m3fn_x4`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.language.float8_e4m3fn_x4.html), and [`float4_e2m1fn_x4`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.language.float4_e2m1fn_x4.html) — collectively, `MXFP_x4`). The `float8_*_x4` types are 32 bits wide and physically contain four `float8` elements. The `float4_*_x4` type is 16 bits wide and physically contains four `float4` elements. As expressed in `_x4` elements, the TensorE maximum tile sizes in NKI code continue to be given by the existing hardware constraints:

| Matrix type | Data type | Implied physical size | Max tile size in code |
|---|---|---|---|
| Stationary | BF16 | [128P, 128F] | [128P, 128F] |
| Stationary | `MXFP_x4` | [512P, 128F] | [128P, 128F] |
| Moving | BF16 | [128P, 512F] | [128P, 512F] |
| Moving | `MXFP_x4` | [512P, 512F] | [128P, 512F] |

This means we allocate data tensors of type `MXFP_x4` in our NKI code with the same shapes as for BF16/FP32, but it's implied they contain 4× more contraction elements.

Now let's examine a BF16 tile destined to be quantized into a max-sized moving tile for Matmul-MX (`[128P, 512F] MXFP_x4`). The following concepts are equally applicable to the stationary tile whose max size is `[128P, 128F]`.

Since a 4×-larger contraction dimension is supported, we'll start with a BF16 tile of size `[512, 512]`. To help us in the subsequent step, we'll also view it as being sectioned into 4 regions of 128 rows (reshaped as `[4, 128, 512]`). This view is mathematical (not residing in any particular memory).

<Frame>
  <img src="/images/nki/img/deep-dives/mxfp84-matmul-guide-1.png" alt="BF16 tile reshaped into [4, 128, 512] for MX preparation" />
</Frame>

As explained in the [Trainium3 architecture guide](/nki/guides/architecture/trainium3_arch), we must take 4 elements originating 128 apart on the contraction axis and pack them together on the SBUF free dimension. Call this "interleaving".

<Frame>
  <img src="/images/nki/img/deep-dives/mxfp84-matmul-guide-2.png" alt="Interleaved SBUF layout with packed elements along the free dimension" />
</Frame>

The SBUF shape has become `[128P, 2048F]`. In a subsequent code example we'll see that it's useful to view/reshape this as `[128P, 512F, 4F]`, making it clear we have 512 groups of 4 packed elements.

Next, let's Quantize-MX this tile, which preserves the layout but packs groups of 4 free-dimension elements into a single `MXFP_x4` element. Quantize-MX doesn't support an FP4 output but Matmul-MX does support FP4 input.

<Frame>
  <img src="/images/nki/img/deep-dives/mxfp84-matmul-guide-3.png" alt="Quantized MXFP_x4 tile with packed elements shown in red" />
</Frame>

The shape is now `[128P, 512F]`, the max moving-tile size we aimed for. Each `MXFP_x4` element physically contains four quantized elements from the original tile. Each TensorE processing element ingests enough data to perform four FP4/FP8 multiply-accumulate operations, which is why four elements from the original contraction axis must be packed together in this fashion.

**Space-allocation rules for quantized `MXFP_x4` data tiles:**

```text
Unquantized interleaved data tile = [P, F] BF16 in SBUF
MX quantized data tile           = [P, F // 4] MXFP_x4 in SBUF
```

### Scale tensor

Let's revisit the BF16 tile with the interleaved SBUF layout — this time with one of the `[8P, 4F]` scaling groups overlaid.

<Frame>
  <img src="/images/nki/img/deep-dives/mxfp84-matmul-guide-4.png" alt="Scaling group overlay on the interleaved BF16 tile" />
</Frame>

MX scales are represented using a `UINT8` tile containing one element for each scaling group. As explained in the Trainium3 architecture guide, we view the partition dimension of SBUF as being split into 4 quadrants of 32 partitions each. Scales must be placed in the quadrant from which the corresponding scaling group originated.

<Frame>
  <img src="/images/nki/img/deep-dives/mxfp84-matmul-guide-5.png" alt="MX scale tensor allocated across four SBUF quadrants" />
</Frame>

The allocated shape is `[128P, 512F]` despite the underlying useful shape being `[16P, 512F]`. See the [`quantize_mx` API](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.quantize_mx.html) for an example of how to improve memory usage by packing scales from other quantized tensors into the same allocation.

**Space-allocation rules for quantized MX scale tiles:**

```text
Unquantized interleaved data tile = [P, F] BF16 in SBUF

If P <= 32 (oversize optional)
MX quantized scale = [P // 8, F // 4] UINT8 in SBUF

If P > 32 (oversize required)
MX quantized scale = [P, F // 4] UINT8 in SBUF
```

A few notes about the example:

- The `MXFP_x4` packed data types are custom to NKI and aren't supported in Torch. We mimic the packed data using `uint8` in Torch and simply view it as `MXFP_x4` in the kernel.
- The `load_scales_scattered()` helper reads contiguously packed offline scales from HBM and spreads them across partition-dim quadrants.
- The PSUM output tile is allocated with data type BF16 to indicate the desired output data type of the Matmul-MX. Matmul-MX ([`nisa.nc_matmul_mx`](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/api/generated/nki.isa.nc_matmul_mx.html)) supports both BF16 and FP32 output dtypes.

The host code that calls this kernel follows the same structure all subsequent examples use — see [`mx_toplevel.py`](https://github.com/aws-neuron/nki-samples/blob/main/src/nki_samples/tutorials/mxfp-matmul/mx_toplevel.py) for `run_offline_quantized_matmul_mx_test`.

- `generate_stabilized_mx_data()` generates MX data on the host. "Stabilized" means the data is randomly generated but injected with certain properties to allow lossless quantization/dequantization, including constraining the data to be in the FP4/8 range. It returns MX data as `ml_dtypes` FP4/FP8, the same data packed into `uint` to mimic `MXFP_x4` packing (suitable for sending to a NKI kernel), MX scales, and a corresponding unquantized FP32 tensor. The input shape argument specifies the unquantized shape. Because the unquantized tensor is viewed as being in the required layout for MX operations, generating an MX data tile of maximum size requires specifying an unquantized free dimension that's 4× larger. In this example the moving unquantized shape is `[128P, 2048F]` and the function returns a `[128P, 512F]` packed MX data tensor.
- `nc_matmul_mx_golden()` is a utility that mimics the hardware's Matmul-MX operation — useful for verifying the hardware output. It assumes the input tensors meet the SBUF layout requirements and the data tensor is packed to mimic `MXFP_x4`, so it can directly accept MX data generated by `generate_stabilized_mx_data()`.
- `compare_and_print_results()` uses `numpy.allclose()` to check data correctness and print the tensors to stdout.
- Although this is a single-tile Matmul-MX, larger MX tensors can be multiplied by using the tiling techniques shown in the non-MX [Matrix multiplication tutorial](/nki/guides/tutorials/matrix_multiplication).

## SBUF layout using strided access

Here we present two techniques for establishing the interleaved layout required for MX operations. Both produce the same result but have different performance trade-offs. Think of them as tools in a toolbox — use the one that's appropriate for your situation.

These techniques operate on unquantized tensors (BF16 in these examples) as the layout must be established before calling Quantize-MX. If you already have offline MX weights (already quantized), establish the required layout offline so you can perform a direct load to SBUF.

### VectorE/ScalarE strided access

Use either VectorE or ScalarE to write data to SBUF in the required layout. The simplest operation is a `TensorCopy`, but it's usually more performant to apply the strided access pattern to some prior useful computation already occurring on these engines.

For completeness, the example loads an HBM tensor to SBUF prior to rearranging the data on-device using an SBUF-to-SBUF `TensorCopy`. The load is needed for a standalone executable example but in practice your data should already be in SBUF from some previous operation. The `TensorCopy` strided access pattern is the key takeaway.

The `TensorCopy` source could be PSUM if you want to rearrange the data immediately after a prior matmul.

### DMA strided access

DMA a tensor from HBM to SBUF using a strided access pattern. Conceptually similar to the above except the source of the copy is in HBM. Typically significantly slower than on-device techniques, but useful in heavily compute-bound workloads where the DMA may overlap with compute.

## Packing scale values

As discussed in **Scale tensor**, each element of a scale tensor corresponds to a group of 32 elements in the unquantized source tensor. Each scaling group spans 8 partitions with 4 free elements per partition, giving scale tensors a logical size of `[P // 8, F // 4]`. However, due to connectivity constraints between SBUF and VectorE, scale values must be placed in the same quadrant as their corresponding scaling group. When the unquantized source tensor spans multiple partitions (that is, `src.shape[0] > 32`), the scale tensor has physical shape `[P, F // 4]`. Only the first 4 partitions (= 32 partitions per quadrant divided by 8 partitions per scaling group) of each quadrant are occupied, leaving the remaining 28 unused.

Quantize-MX lets you utilize some of this space by packing scale values from multiple Quantize-MX calls. Quantize-MX and Matmul-MX support writing/reading scales at an offset of 0, 4, 8, or 12 within each partition, so you can pack scale values from up to four tensors into a single tile. ## Additional tips

- Plan where in your design you'll pay the cost of interleaving the data. Ideally, minimize the cost by finding existing, prior compute on which you can apply the strided access pattern, or find existing compute against which you can overlap the interleave process. For offline MX weights, prepare the layout offline on CPU so you can load the data to SBUF directly in a contiguous/unstrided fashion.
- As with all compute on Neuron, it's generally performant to spread it across multiple engines operating in parallel. Given that Quantize-MX runs exclusively on the VectorE, a bit more care may be needed to alleviate VectorE contention by becoming familiar with operations that may be relegated to other engines, like ScalarE.
- The TensorE operates at double the clock frequency of VectorE, so Matmul-MX produces data at double the rate Quantize-MX can consume it. It may seem that the TensorE could be back-pressured in a situation where a Matmul-MX quickly feeds a subsequent Matmul-MX (since you must Quantize-MX in between at half the speed), but that only happens for small tensors. Larger tensors require tiled matrix multiplication, which inherently reuses input (quantized) tiles, allowing time for prior matmul output data to be quantized.
- Matmul-MX supports PE-tiling (row-tiling only) where matmuls with a small (≤ 64) contraction-dimension (partition-dimension) may be parallelized on the TensorE. This becomes more relevant for MX since a 4×-larger effective contraction-dimension is supported, meaning it's useful for an `MXFP_x4` contraction-dimension ≤ 64 or an equivalent unquantized contraction-dimension ≤ 256.
